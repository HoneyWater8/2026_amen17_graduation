# 2026-09-27 · 전체 최적화 검토와 기존 Blob 삭제

> 현재 영상 제공은 유지하면서 초기 전송량·상시 애니메이션·이미지·캐시를 검토했다. 사용자 요청으로 이전 Vercel Blob 파일과 저장소를 삭제했다. 최적화 구현과 커밋·푸시는 하지 않았다.

## 검토 조건과 실측

- 대상: main `a6f458e`, 실배포 `https://2026amen17graduation.vercel.app/`, JS `/assets/index-C9bvG6bZ.js`.
- Chrome 새 프로필, 390×844, DPR 3. CPU·네트워크 제한 없이 데스크톱에서 모바일 화면 크기로 측정했다. 실제 휴대폰 성능이나 전체 방문자의 Core Web Vitals를 뜻하지 않는다.
- 성능 측정에서는 GA4·Vercel Analytics를 차단하지 않았다. Chrome Network의 `encodedDataLength`를 집계했다. 썸네일 셔플·네트워크 상태에 따라 방문별 결과는 달라질 수 있다.
- 봉투를 열기 전 50개 요청, 수신 약 **1.15MB**. 폰트 23개 **511KB**, Google Fonts CSS **39KB**, 앱 JS **77KB**, GA 스크립트 **177KB**, 이미지 약 **338KB**였다. 외부 Google 전송량까지 포함한 값이며 모두 Vercel 사용량인 것은 아니다.
- 첫 콘텐츠 표시 0.892초, 해당 실행의 LCP 1.060초, 초기 CLS 약 0.00014. 초기 53ms·60ms long task가 각각 한 번 있었다. 이 한 번의 측정만으로 느린 기기에서의 성능을 보장하지 않는다.
- 봉투 전·표지·여정·마지막 섹션 모두 MP4 요청 0건. 앱 전체 DOM 837개. 사진 확대본은 클릭 전 요청하지 않았고 카카오 SDK도 초기 요청에 없었다.
- 사진 캐러셀은 4개 중 사진이 여러 장인 3개가 자동 이동한다. 화면 밖에서도 3초 동안 rAF 콜백 540~546회, 스타일 재계산 약 181회가 발생했다. 모션 감소 설정에서도 rAF 콜백은 543회로 계속되며 스타일 변경만 멈췄다.
- 원자료·점검 스크립트는 Git 제외 `assets/video-work/optimization-audit.json`, `asset-audit.json`, `audit-page.cjs`에 있다. 공개 문서에 인증 값이나 임시 서명 URL을 저장하지 않는다.

## 우선순위와 제안 범위

### 1. 화면 밖 캐러셀의 프레임 반복 중지 — 효과 명확, 우선 적용

`FE/src/components/common/PhotoRail.tsx`의 `paused`에는 화면 진입·봉투 상태가 없으며 `tick`은 정지 중에도 다음 프레임을 예약한다. `Journey.tsx`도 `active`를 PhotoRail에 전달하지 않는다.

- 봉투 개봉, 캐러셀의 화면 진입, 탭 표시, 라이트박스·모션 감소 상태를 기준으로 rAF 자체를 시작·취소한다.
- 재개할 때 시간 기준을 초기화해 긴 정지 후 위치가 튀지 않도록 한다. 기존 위치·관성·카드 stride·세로 스크롤·탭 동작은 유지한다.
- `ScrollHint.tsx`의 보이지 않는 무한 CSS 애니메이션도 표시 중에만 실행할 수 있다.
- 합격 기준: 봉투 전·캐러셀이 화면 밖일 때 캐러셀 프레임 반복 0회, 화면에 들어오면 기존 속도·드래그로 재개. 라이트박스와 모션 감소에서도 중지.

### 2. 정적 파일의 브라우저 캐시 — 변경 범위 작음

실배포의 해시 JS/CSS, 사진, 포스터, 실링왁스 이미지가 모두 `Cache-Control: public, max-age=0, must-revalidate`였다. Vercel CDN HIT와 브라우저의 장기 캐시는 별개다. 현재도 조건부 요청으로 본문 재전송을 피할 수 있으므로 매번 전량 다운로드한다고 설명하지 않는다.

- `FE/vercel.json`에 `/assets/`의 해시 파일을 대상으로 `max-age=31536000, immutable`을 설정한다.
- 사진·포스터는 현재 파일명이 고정이므로 해시/버전 경로 도입 후 장기 캐시하거나 우선 짧은 TTL을 적용한다. 고정 경로에 무조건 1년 캐시를 주면 교체 사진이 늦게 반영될 수 있다.
- HTML은 최신 배포를 확인하도록 재검증을 유지한다. 캐시를 바꾼 뒤 재방문 요청·새 배포 갱신을 확인한다.
- 근거: [Vercel Cache-Control](https://vercel.com/docs/caching/cache-control-headers).

### 3. 폰트 경량화 — 초기 전송 절감 여지가 가장 큼

`FE/index.html`은 Cinzel Decorative 400/700/900, Nanum Myeongjo 400/700/800을 요청한다. 실제 측정에서 내려받은 폰트는 Cinzel 400 및 Nanum 400/700의 총 23개 조각이다. **안 쓰는 굵기는 이미 폰트 본문을 받지 않는다.** 굵기 목록만 줄여서 511KB 전체를 절감할 수는 없으며 우선 CSS 크기를 줄이는 효과다.

- 실제 사용 굵기만 선언하고, 동일 서체에서 사이트에 쓰이는 글자만 남긴 WOFF2 생성·직접 제공을 검토한다.
- 명단·초원명·공유창·오류/이어보기 문구·숫자까지 포함하고 콘텐츠 변경 시 재생성하는 절차가 필요하다. 서체 라이선스도 동봉한다.
- 현재 Google Fonts도 문자 범위별 부분 로딩을 하고 있다. 추가 절감량은 사이트 전용 부분 폰트를 생성한 뒤 측정해야 한다.
- 모양·굵기·글자 누락·줄바꿈 검증 후 적용하며, 기존 `display=swap`과 봉투 애니메이션 시간은 유지한다.
- 근거: [웹 폰트 로딩 최적화](https://web.dev/articles/optimize-webfont-loading).

### 4. 화면에 가까워질 때 포스터·사진 로딩

`VideoSlot.tsx`는 MP4 연결은 미루지만 포스터 11장(파일 합계 **163,112B**)을 모두 즉시 연결한다. 봉투 전에도 첫 사진 레일의 썸네일 일부가 브라우저의 lazy 임계값 안에 있어 내려온다.

- 개봉 이후 해당 영역에 접근할 때 포스터를 연결하고, 사진 레일 역시 화면 근처에 온 뒤 이미지 요청을 허용한다. `IntersectionObserver`의 여유 범위로 빠른 스크롤에서도 빈 화면을 줄인다.
- 초기 단계에서 포스터 약 163KB와 미리 받아지는 사진 요청을 늦출 수 있다. 끝까지 열람할 때 총량이 같은 경우도 있으므로 전체 트래픽이 항상 그만큼 줄어드는 것은 아니다.
- 영상 src·단일 재생·화질 전환 로직과 분리해서 적용한다. 사진을 항상 화면에 들어온 뒤에만 받도록 지나치게 늦추지 않는다.
- 근거: [Intersection Observer](https://developer.mozilla.org/en-US/docs/Web/API/Intersection_Observer_API).

### 5. 정적 이미지 변환 — 실링왁스는 무손실부터

파일 교체 없이 메모리에서 시험 인코딩한 결과다.

| 대상 | 현재 | WebP 시험 결과 | 감소 |
|---|---:|---:|---:|
| 실링왁스 360×300 RGBA | PNG 80,677B | 무손실 37,438B | 약 54% |
| 사진 썸네일 61장 | JPEG 1,098,063B | 품질 78, 866,434B | 약 21% |
| 사진 확대본 61장 | JPEG 11,589,682B | 품질 82, 8,129,624B | 약 30% |

- 실링왁스는 무손실 WebP여서 외형을 유지하면서 약 43KB를 줄일 수 있다.
- 사진은 기존 JPEG를 손실 재압축한 시험이다. 같은 품질 숫자가 같은 시각 품질을 의미하지 않으며 얼굴·단체 사진·작은 글씨 비교가 필요하다. 원본이 있는 사진은 원본에서 변환한다.
- `scripts/resize-photos.py`, `graduation.ts`의 경로 생성, `Seal.tsx`, 자산 경로를 함께 바꾼다. PNG 카카오 OG 이미지는 별도 호환성을 고려한다.
- 확대본 전체 11.59MB가 초기 로딩되는 것은 아니다. 현재도 사진을 눌렀을 때 해당 파일만 받는다.
- 근거: [WebP 이미지 사용](https://web.dev/articles/serve-images-webp).

## 유지할 부분

- R2 직접 전송, 선택 영상의 `preload=auto`, 클릭 전 src 미연결, 숨긴 탭·다른 영상에서 다운로드 중단, 전체화면 HD와 실패 시 경량 복귀를 유지한다. 추가 압축·HLS 전환은 이번 검토에서 우선 과제로 잡지 않았다.
- React를 포함한 앱 JS 수신량은 약 77KB다. 프레임워크 교체·과도한 코드 분할·전면 memo 적용보다 위 항목의 효과가 명확하다.
- GA4와 Vercel Analytics는 현재 서로 다른 통계 목적이 있다. 초기화 변경으로 실제 집계가 깨진 이력이 있으므로 임의 제거·동적 로드 전환은 제안하지 않았다.
- 사진 thumb/full 분리, lazy 이미지, 지연 카카오 SDK, 일회성 Reveal, passive 스크롤 감지는 이미 적용되어 있다.

## 기존 Vercel Blob 삭제

- 사용자 추가 요청: “vercel 블롭은 삭제해도 될 듯”. 이 요청으로 이전의 Blob 백업 보존 지시를 갱신했다. 로컬 원본과 R2에는 삭제를 적용하지 않았다.
- 삭제 전 실배포 번들에서 R2 영상 URL 22개·Blob 호스트 0개 확인. Production/Preview 환경 변수를 내려받아 각각 22개 모두 R2임을 확인했다.
- R2 22개 모두 HEAD 200, 시작·끝 256바이트 Range 206, 로컬 바이트 일치, CORS 및 R2 직접 본문 전송을 재검증했다.
- 대상은 `store_zw4d65fKlIme6aVE` 하나. SDK 목록이 기존 경량·고화질·교체 전 영상 **26개, 989,065,457B**와 일치함을 확인하고 삭제했다. 삭제 직후 SDK 목록은 0개였다.
- CLI 첫 저장소 삭제는 프로젝트 연결을 해제한 뒤 `409 Blob store not empty`를 반환했다. 이후 기존 읽기·쓰기 토큰으로 파일을 지우고 저장소 삭제를 완료했다. 만료/해제된 OIDC를 재사용하지 않았다.
- 최종 CLI는 `Success! Blob store deleted`, 팀 전체 `list-stores --all`은 `No blob stores found`였다.
- 삭제 후 실배포 Chrome에서 간증 1번·감사 합본의 540p 재생, 단일 재생, 최초 MP4 요청 0건을 확인했다. 브라우저 예외는 없었다. 프로젝트 환경 변수는 영상 22개를 유지하며 `BLOB_*` 키는 0개였다.
- CLI가 다시 추가한 `.gitignore`의 중복 `.env*` 규칙을 제거해 `.env.example` 예외를 유지했다. 로컬의 폐기된 Blob 인증 변수와 검증용 임시 환경 파일도 정리했다.
- 현재 버전 영상 22개는 R2에, 원본·full과 교체 전 원본 4편은 로컬에 남아 있다. 과거 Blob 주소를 쓰던 배포는 복구 대상으로 사용하지 않는다.
- Blob 삭제가 이미 발생한 전송 사용량·청구 내역을 초기화한다는 의미는 아니다. 이번 작업에서 요금제 변경·Vercel 직접 배포·커밋·푸시는 하지 않았다.
